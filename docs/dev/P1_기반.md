# P1 기반 설계

## 시연 데이터 단일 시나리오 (2026-11-25, 구현 완료)

기존 시연 자료(6개 단위서비스, 라벨링당 2~4개 개발사항 무작위 생성)를 모두 없애고, 개발사항 하나를 단계별로 보여 주는 자료로 바꿨다. 초기화 방식(머리글 버튼, 잠금, 시연 범위)은 아래 2026-11-22 절과 같다.

| 구분 | 내용 |
|---|---|
| 대상 | `음성링고 / R164PKG_26.12 / 계절·명절 인사말 자동 추천 템플릿 및 예약 일괄 전환 서비스` |
| 구성 | 같은 개발사항을 1~7단계 상태로 7개 생성(이름 같음, 코드 다름, 단계 순서로 정렬). 스냅샷 N은 N단계까지의 자료만 가지며 N단계가 "진행중"이다(7단계는 전부 완료) |
| 관련자 | 허유진(요청, 상품기획(사업 BM)), 이승학(검토, 현장(영업 AM)), 옥수빈(운영·검증, 운용 부서). 이름·회사 메일 주소는 사용자 지정이다. 수집 요청·진행상황 요청의 받는 사람과 회신·문서 전달의 보낸 사람은 이승학이다. 개발사는 회사명만 쓴다(담당자 없음) |
| 일정 | 7개 스냅샷이 같은 일정을 쓴다(같은 메일·문서는 같은 날짜). 기준 일정은 수집 2026-09-30, 착수 10-06, 상용적용 12-10, 완료 12-11이다. 초기화 시점이 완료 일시보다 이르면 완료가 과거가 되도록 전체 일정을 주 단위로 앞당긴다(요일 유지). 예: 2026-11-25에 초기화하면 3주 앞당겨 상용적용 11-19 |
| 코드 | `lib/demo/catalog.ts`(시나리오 원본), `lib/demo/timeline.ts`(일정), `lib/demo/builders.ts`(산출물), `lib/repo/demo-seed.ts`(스냅샷별 적재). 기존 카탈로그 5개 파일 삭제 |

단계별 자료:

| 스냅샷 | 단계 상태 | 들어 있는 자료 |
|---|---|---|
| 1 | 수집 진행중 | 수집 요청 메일 발송 (회신 대기) |
| 2 | 검토 진행중 | 수집 회신(12개 항목, 히스토리 6건, [상충] 1건, 출처 없는 진술 1건), L1 점검(충분 8·부족 4, 질문 5개), 담당자 답 1건 |
| 3 | PRD 진행중 | 담당자 답 5건·보완 메모, PRD v1(시스템 초안: FR 5건·NFR 2건), PRD v2(편집: NFR-03 추가). 공유 전 |
| 4 | Architecture 진행중 | PRD v2 공유, 개발사 `architecture.md` 수신·등록, 검토 리포트(반영 5·부분 3, PRD에 없는 추가 내용 1건, 질문 4개). 공유 전 |
| 5 | QA 진행중 | Architecture 리포트 공유, 개발사 `qa.md`(TC 10건) 수신·등록, 검토 리포트(반영 6·부분 1·미반영 1, 시험 누락 3건). 공유 전 |
| 6 | 진행상황 진행중 | QA 리포트 공유, 진행상황 요청·회신 2회(개발검증시험 하루 지연과 운용검증시험 착수일 변경 이력), 상용적용 예정 |
| 7 | 완료 | 진행상황 3회차(상용적용 실적), 진행상황 공유, 완료 처리 |

결정 사항:

- 스냅샷의 단계 상태는 화면 동작과 일부 다르다. 실제 화면은 Architecture·QA md가 등록되면 그 단계를, 진행상황 회신이 해석되면 6단계를 곧바로 완료로 바꾼다. 스냅샷은 "N단계 화면에서 N단계 자료를 보여 준다"는 목적에 맞춰 리포트 공유 전(4·5단계), 상용적용 전(6단계)을 진행중으로 둔다. 기존 시연 자료와 같은 방식이다.
- 초기화할 때마다 내용이 같다(무작위 요소 없음). 개발사항 코드만 새로 받는다.
- 관련자 3명의 실제 메일 주소가 공유 받는 사람 기본값에 들어간다. 실제 Gmail 모드에서 시연 개발사항은 본인 주소로만 발송되므로(TC-P1-27) 관련자에게 실제 메일이 나가지 않는다.
- 시연 자료의 수치(민원 월 40건, 5만 회선 등), 논의 이력, 개발사명, 개발사 문서는 모두 합성이다.

## 다중 사용자·시연 데이터 범위 변경 (2026-11-22, 구현 완료·배포 대기)

- 기준: [상단 초기화·다중 사용자 계획](../proposals/2026-11-22_상단-초기화-다중사용자-계획.md). 업무 데이터는 공유하고 로그인·메일 설정만 사용자별로 나눈다. 운영 방법: [배포 가이드 10장](../guides/배포-가이드.md#10-다중-사용자-설정-약-5명)

| 구분 | 내용 |
|---|---|
| 로그인 | `AUTH_USERS`(ID 목록) + `USER_<ID>_PASSWORD_HASH`(scrypt). 없으면 기존 `LOGIN_ID`/`LOGIN_PASSWORD`. 세션 토큰 `id.만료.자격버전.서명` — 비밀번호 해시 변경·계정 삭제 시 무효. 같은 ID 5회 실패 시 15분 차단(인스턴스 메모리) |
| 사용자 문맥 | `respond()`가 세션 쿠키로 사용자를 찾아 AsyncLocalStorage에 넣고, `getMailConfig()`가 그 사용자의 `USER_<ID>_GMAIL_*`를 읽는다. 다중 사용자인데 사용자가 없으면 `unconfigured` |
| 메일 | 수신 위치·마지막 확인 시각은 `app_state`의 `키:계정`, 폴링 잠금과 발송 한도는 Gmail 계정별. 외부 크론(GET `/api/mail/poll?secret=`) 제거 |
| 시연 범위 | `nodes.is_demo`, `mails.is_demo`. 시연 노드 아래 생성은 상속, 시연↔실제 간 이동 거부. 시연 개발사항의 실제 Gmail 발송은 본인 수집·Gmail 주소로만 |
| 초기화 | 머리글 버튼 → `POST /api/demo/seed`. DB 잠금(`app_state.demo_reset_lock`, 5분 만료) → 시연 개발사항에 매칭된 실제 수신 메일을 미분류로 되돌림 → 시연 메일·노드 삭제 → 재생성. 생성 실패 시 시연 데이터를 다시 비우고 오류 표시. 코드 시퀀스는 되돌리지 않음 |
| DB | 마이그레이션 `0006_demo_scope_accounts`: `nodes.is_demo`, `mails.is_demo`, `mails.account` 추가. 적용 시점의 기존 자료는 모두 시연으로 표시(사용자 확인) |
| 화면 | 머리글 `시연 데이터 초기화` 버튼과 사용자 이름, 설정 화면은 로그인 사용자의 메일 설정만 표시(기존 설정 화면의 초기화 영역 제거) |
| 내 메일 설정 | 설정 화면에서 본인의 Gmail 주소·앱 비밀번호·수집 요청 주소 수정. `GET/PUT /api/settings/mail`, 테이블 `user_settings`(마이그레이션 `0007_user_settings`). 앱 비밀번호는 AES-256-GCM 암호화(`lib/secret-box.ts`, 키 `SETTINGS_ENCRYPTION_KEY` 또는 `AUTH_SECRET` 파생), 응답에는 설정 여부만. 우선순위: 내 입력값 → 관리자 환경 변수. `respond()`가 요청마다 합친 값을 요청 문맥에 넣는다. 첫 로드 전에는 입력 칸을 막아 빈 값 저장을 방지 |

## 1. 범위

| 포함 | 제외 |
|---|---|
| 더미 로그인(D-03), 트리 CRUD·드래그 이동, 개발사항 코드(`DEV-0001`), 7단계 진행 그래프와 수동 상태 변경, 완료 버튼, 이력, 대시보드, DB 연결(Neon/PGlite), 마이그레이션 | 메일·LLM (P2~), 실제 배포 |

## 2. 구성

- **프레임워크:** Next.js 16 (App Router, `proxy.ts`, Cache Components), TypeScript, Tailwind 4
- **DB:** Drizzle ORM
  - `DATABASE_URL`이 `postgres…`이면 Neon HTTP
  - 그 밖에는 PGlite(로컬 파일, 시험에서는 메모리)
- **인증:** HMAC-SHA256으로 서명한 쿠키(`aidd_session`, 14일) 하나만 씁니다. 세션 저장소는 없습니다.

## 3. DB (마이그레이션 `0001_init`)

| 테이블 | 열 |
|---|---|
| `nodes` | id, type(service/label/item), name, parent_id(삭제 시 하위까지), sort_order |
| `dev_items` | node_id, code(유일, 시퀀스로 부여하며 재사용하지 않음), keywords, search_period, memo, completed_at |
| `stages` | item_id, stage, status(pending/in_progress/done), updated_at |
| `events` | item_id, kind, message, created_at |

## 4. 규칙

- **배치:** 단위서비스는 최상위, 라벨링은 단위서비스 아래, 개발사항은 라벨링 또는 단위서비스 아래(Q-01)에 둡니다. 서버와 화면 양쪽에서 검사합니다.
- **현재 단계:** 완료되지 않은 첫 단계입니다. 순서는 강제하지 않습니다(Q-04).
- **파일명:** `{단위서비스}_{라벨링}_{개발사항}_{종류}.md`. 공백과 금지 문자는 `_`로 바꿉니다.
