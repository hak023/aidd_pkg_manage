# P4 Architecture·QA 설계

- 상태: 완료 (2026-11-21). 사용자 시험(TC-P4-U1) 대기
- 기준: 서비스 정의 v0.2 — 3장 단계 4·5, 4.2 태그 없는 전달 메일, 4.6 공유 메일, 5.1 L3·L4·L5, 5.4 검토 리포트 양식
- 시험: [docs/test/P4_시험.md](../test/P4_시험.md)

## 1. 범위

**포함**

1. **문서 등록:** 전달 메일의 md 첨부를 Architecture 또는 QA 문서로 등록합니다.
   - **태그 있는 메일:** 개발사항은 정해져 있으므로 유형만 판별합니다. 파일명·제목·내용의 키워드로 먼저 판단하고, 애매할 때만 L3를 씁니다.
   - **태그 없는 메일:** L3로 유형과 개발사항을 함께 추정합니다.
     - 확신도가 0.7 이상이면 자동으로 지정하고 등록합니다(매칭 방법: `llm`).
     - 0.7 미만이면 미분류함에 남기고, 추정 결과를 "추천"으로 보여 줍니다.
   - **수동 등록:** 개발사항 화면에서 아직 등록하지 않은 첨부를 골라 "Architecture로 등록" 또는 "QA로 등록"을 누릅니다. **md 내용을 직접 붙여 넣어** 등록할 수도 있습니다. 로컬 Gmail이 막혀 있는 동안의 대안입니다.
   - **개정본:** 다시 등록하면 새 버전이 됩니다.
2. **단계 진행:** 등록되면 해당 단계(4 또는 5)를 완료합니다. 완료 조건 "md 등록"을 따릅니다.
3. **L4·L5 검토 리포트:** 등록하면 자동으로 생성합니다.
   - 입력: 최신 PRD + 대상 문서. QA 검토에는 Architecture를 넣지 않습니다(8장 결정 참고).
   - "리포트 다시 생성" 버튼이 있습니다.
   - PRD가 없으면 만들지 않고 이력에 안내를 남깁니다.
4. **리포트 편집:** PRD와 같은 편집기를 씁니다. 저장하면 새 버전이 됩니다.
5. **공유:**
   - 제목은 4.6 양식을 따릅니다.
   - 첨부: 대상 문서 최신본 + 선택한 리포트 버전
   - 받는 사람 기본값: 관련자
   - 공유는 단계를 바꾸지 않습니다(이미 등록 시 완료). 이력만 남깁니다.
6. **수집 회신 직접 입력 (P3 보완):** 회신 본문을 붙여 넣어 수집 회신으로 등록합니다. 사용자 시험 TC-P3-U1을 Gmail 없이 하기 위한 기능입니다.

**제외:** 진행상황(P5)

## 2. 판정과 리포트 형식 (5.4)

- **판정:** `반영` / `부분` / `미반영` / `확인 불가`
- **요구사항 목록:** PRD 표에서 `FR-xx`, `NFR-xx` 행을 코드로 추출합니다. LLM이 요구사항마다 한 행씩 판정하고, 빠진 요구사항은 "확인 불가(응답 누락)"로 채웁니다.
- **md 작성:** LLM은 JSON만 돌려주고, md는 코드가 만듭니다. 요약 건수를 정확하게 맞추기 위해서입니다.

```markdown
# {개발사항} {Architecture|QA} 검토 리포트
- 대상 문서: {파일명} (등록 {일시}, v{n}) · 기준 PRD: v{n} · 작성: AX_AIDD 시스템 ({모델})
> 문서상 대조 결과이며 실제 시험 합격을 뜻하지 않습니다. 판단은 검토자가 합니다.
## 1. 요약 (반영 n건 / 부분 n건 / 미반영 n건 / 확인 불가 n건)
## 2. 요구사항별 대조
| 요구사항 | 판정 | 대상 문서의 근거 위치 | 설명 |
### 시험 누락 점검 (QA만: 예외·실패 / 비기능 / 회귀)
## 3. PRD에 없는 추가 내용 (범위 확인 필요)
## 4. 추가 확인 필요 사항 (개발사에 보낼 질문)
## 5. 검토자 메모 (사용자 편집)
```

## 3. LLM

| 작업 | 모델 설정 | 출력 (JSON) |
|---|---|---|
| L3 분류 | `GEMINI_MODEL_CLASSIFY` | `{ docType: arch/qa/other, itemCode, confidence 0~1, reason }`. itemCode는 주어진 목록 안의 코드만 허용 |
| L4/L5 점검 | `GEMINI_MODEL_DOCREVIEW` | `{ rows: [{ id, verdict, location, note }], extras: [], questions: [], gaps: [{ category, note }] }` |

**공통**
- 문서 내용은 `<data>`로 감싸고, 그 안의 지시는 무시합니다(G-04).
- 형식이 틀리면 1회 재시도합니다. 실패하면 이력에 기록하고, 리포트는 만들지 않습니다(G-05).
- 문서는 앞부분 6만 자까지만 보냅니다.

**모의 응답**
- L3: 키워드로 유형을 판단합니다. 개발사항은 이름 단어가 2개 이상 겹치고 하나로 정해질 때 확신도 0.8, 아니면 0.3입니다.
- L4/L5: 요구사항 단어와 문서 단어가 겹치는 비율로 판정합니다(60% 이상 반영, 25% 이상 부분, 그 밖은 미반영).

## 4. DB (마이그레이션 `0004_docs`)

| 변경 | 내용 |
|---|---|
| `documents` 열 추가 | `source_mail_id`(전달 메일), `attachment_id`(등록한 첨부, 중복 등록 확인용), `base_doc_id`(리포트의 대상 문서), `prd_doc_id`(리포트의 기준 PRD) |
| `mails` 열 추가 | `suggestion`: 미분류 메일의 L3 추정 결과 (JSON) |

## 5. API

| 메서드 · 경로 | 내용 |
|---|---|
| `GET /api/items/[id]/docs?kind=arch` | 등록된 버전 목록, 등록 후보 첨부 |
| `POST /api/items/[id]/docs` | 등록 `{ kind, attachmentId }` 또는 `{ kind, content, filename }` → 새 버전, 단계 완료, 리포트 자동 생성 |
| `POST /api/items/[id]/doc-review` | 리포트 다시 생성 `{ kind }` |
| `GET·POST /api/items/[id]/share?kind=prd/arch/qa` | 공유 기본값과 발송. 기존 `prd/share`를 대체 |
| `POST /api/items/[id]/manual-reply` | 수집 회신 직접 입력 `{ text }` |

## 6. 화면

**4·5단계 선택 시 "개발사 문서" 카드**
- 등록된 버전 선택과 미리보기
- 등록 후보 첨부와 등록 버튼
- 직접 붙여 넣기

**"검토 리포트" 카드**
- PRD 편집기와 같은 구성
- "리포트 다시 생성" 버튼
- 공유 버튼: 대상 문서와 리포트를 함께 첨부

**미분류함:** L3 추천(개발사항, 유형, 확신도, 이유)을 표시하고, 지정할 개발사항 선택란에 미리 넣어 둡니다.

**수집 검토 카드:** "회신 직접 입력"

## 7. 완료 기준

1. 시뮬레이터(모의 LLM)에서 다음이 브라우저로 끝까지 진행됩니다.
   - 태그 있는 Architecture·QA 전달 → 자동 등록 → 4·5단계 완료 → 리포트 생성 → 편집 저장 → 공유
   - 태그 없는 전달 → 미분류함 추천 → 지정 → 등록
2. 실제 Gemini로 L3와 L4·L5가 성공합니다. 응답 형식이 맞아야 하고, 샘플 Architecture에 의도적으로 넣은 PRD와 다른 점(로그 보관 1년 vs 180일, 계정 병행 등)이 리포트에서 지적되어야 합니다.
3. 점검 실패가 리포트를 만들지 않고, 등록과 단계는 유지됩니다.
4. 자동 시험, typecheck, lint, build가 통과합니다.

| 3. 점검 실패 시 등록·단계 유지, 리포트 미생성 | 충족 (TC-P4-14) |
| 4. 자동 시험·정적 점검 | 충족 (63건, typecheck, lint, build) |

## 8. 결정 기록

| 일자 | 결정 | 근거 |
|---|---|---|
| 2026-11-21 | 리포트 md는 코드가 만들고, LLM은 판정 JSON만 | 요약 건수, 양식, 면책 문구 정확성 |
| 2026-11-21 | 유형 판별은 키워드 우선, 애매할 때만 L3 | 비용·지연 감소, 태그 있는 메일은 대부분 파일명으로 판별됨 |
| 2026-11-21 | 자동 지정 기준 확신도 0.7 | 서비스 정의 4.2 "확신도가 높으면 자동 등록". 잘못 붙으면 사용자가 되돌리기 어려우므로 보수적으로 |
| 2026-11-21 | 수집 회신·개발사 문서 직접 입력 추가 | 로컬 Gmail 차단 중에도 실무 시험이 가능하도록 |
| 2026-11-21 | **QA 점검(L5)에는 Architecture를 넣지 않음** (설계 변경) | 실제 Gemini 시험에서, 넣으면 프롬프트로 금지해도 설계서를 시험 커버리지 근거로 인용함. 서비스 정의 5.1에서 Architecture는 선택 입력 |
| 2026-11-21 | **L4/L5 응답 스키마에서 요구사항 ID를 enum으로, 행 수를 요구사항 수로 고정** | 실제 Gemini 시험에서 판정을 다른 요구사항 ID에 붙인 사례 발생 |
| 2026-11-21 | 공유 API를 `/api/items/[id]/share?kind=`로 통합하고, PRD·리포트 편집 화면을 공용 `DocPanel`로 | 같은 동작(버전·편집·공유)을 한 곳에서 유지 |
