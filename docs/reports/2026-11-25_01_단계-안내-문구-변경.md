## 1. 요청 내용

frontend 문구 변경. "회사 메일에서 개발사의 설계서 메일을 태그를 붙여 Gmail로 전달합니다."를 "개발사로부터 architecture.md 파일을 요청합니다."로 바꾸고, 관련 문구를 모두 바꾼다. Architecture 단계 외의 단계에도 단계에 맞게 적용한다.

## 2. 수행 내용

화면 문구만 바꿨다. 동작(전달 메일 수신·자동 등록)은 그대로다.

| 위치 | 이전 | 이후 |
|---|---|---|
| 4단계 "사용자가 할 일" | 회사 메일에서 개발사의 설계서 메일을 태그를 붙여 Gmail로 전달합니다. | 개발사로부터 architecture.md 파일을 요청합니다. |
| 5단계 "사용자가 할 일" | 시험항목서 메일을 태그를 붙여 Gmail로 전달합니다. | 개발사로부터 qa.md 파일을 요청합니다. |
| 4·5단계 "개발사 … 문서" 카드 안내 | 회사 메일에서 "전달용 제목"을 붙여 Gmail로 전달하면 자동으로 등록됩니다. | 개발사로부터 {architecture.md / qa.md} 파일을 요청합니다. 받은 파일은 "전달용 제목"을 붙여 Gmail로 보내면 자동으로 등록되고, … (단계에 따라 파일명이 바뀜) |
| "전달용 제목 복사" 버튼 툴팁 | 개발사 문서를 회사 메일에서 Gmail로 전달할 때 제목에 붙이면 … | 개발사로부터 받은 architecture.md·qa.md 파일을 Gmail로 보낼 때 제목에 붙이면 … |

- 두 단계의 뒤 문장("점검 리포트를 확인·편집하고 공유합니다.")은 그대로 두었다.
- 1·2·3·6·7단계에는 "개발사 문서를 전달"하는 문구가 없어 바꾸지 않았다.
- 문서 카드와 버튼 툴팁에는 "전달용 제목을 붙여 보내면 자동 등록된다"는 설명을 남겼다. 이 설명이 없으면 "전달용 제목 복사" 버튼의 쓰임을 화면에서 알 수 없기 때문이다.

**검증**

- 변경한 3개 파일: eslint 통과, typecheck 오류 없음.
- `npm test`: 6개 파일 82건 통과. `tests/demo-seed.test.ts` 1개 파일은 불러오기 단계에서 실패했다(아래 참고).
- `npm run typecheck` 전체: 오류 19건, 모두 `src/lib/repo/demo-seed.ts`와 `tests/demo-seed.test.ts`에서 발생.
- 브라우저 화면 확인은 하지 않았다.

**참고 — 작업 중 발견한 것**

- 작업을 시작할 때 워킹 트리는 깨끗했는데, 도중에 `web/src/lib/demo/` 아래 8개 파일의 삭제가 스테이징되고 `timeline.ts`·새 `types.ts`·새 `catalog.ts`가 생겼다. 이 요청에서 한 일이 아니며, 다른 세션이 시연 데이터를 수정하는 중으로 보인다. 위 typecheck·테스트 실패는 이 진행 중인 변경 때문이다.
- 실패가 기존 상태인지 확인하려고 `git stash` → typecheck → `git stash pop`을 한 번 실행했다(HEAD 기준 typecheck 오류 0건). 이 과정에서 위 삭제 8건의 스테이징이 풀렸고, `git rm --cached`로 원래 상태(삭제 8건 스테이징)로 되돌렸다. 파일 내용은 바뀌지 않았다. 다만 stash가 걸려 있던 동안(typecheck 1회 실행 시간)은 삭제된 파일들이 워킹 트리에 잠시 되살아났다.

## 4. 결정 사항 / 미결 사항

**결정**

- 4단계 파일명 표기는 요청대로 `architecture.md`, 5단계는 같은 형식으로 `qa.md`.

**미결 (사용자 확인 필요)**

- 5단계 파일명 표기 `qa.md`가 맞는지 (예: `QA.md`, `시험항목서.md`).
- 문서 카드와 툴팁에 남긴 "전달용 제목을 붙여 Gmail로 보내면 자동 등록" 설명도 빼야 하는지.
- 서비스 정의 v0.2(Q-03)와 메일 연동 가이드에는 "회사 메일에서 Gmail로 전달" 표현이 남아 있다. 요청이 frontend 문구여서 바꾸지 않았다.
- `web/src/lib/demo/`를 수정 중인 다른 세션이 stash 시점에 영향을 받지 않았는지.
