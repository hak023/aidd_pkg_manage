## 1. 목적

3단계(PRD 작성), 4단계(Architecture 검토), 5단계(QA 검토)가 **어떻게 이루어지는지**를 화면에서 바로 알 수 있게 합니다. LLM에 보내는 프롬프트를 요약이 아닌 **원문 그대로** 웹 페이지에 공개합니다.

## 2. 현재 상태

| 항목 | 현재 |
|---|---|
| 프롬프트 위치 | 코드에만 있음. PRD는 `web/src/lib/llm/prd.ts`(`PRD_SYSTEM`, `buildPrdPrompt`), Architecture·QA는 `web/src/lib/llm/docreview.ts`(`DOCREVIEW_SYSTEM`, `buildDocReviewPrompt`) |
| 4·5단계 프롬프트 차이 | 하나의 프롬프트를 함께 씀. 판정 초점 문장과 "시험 누락 점검(gaps)" 줄만 다름 |
| 화면 표시 | 단계 설명 카드의 "시스템이 하는 일" 한 문장, 문서 버전 메모와 이력의 모델명뿐. 프롬프트는 나오지 않음 |
| 실제 전송 기록 | 저장하지 않음. 어떤 문서가 어떤 프롬프트로 만들어졌는지 나중에 확인할 수 없음 |
| 모의 LLM | 프롬프트를 쓰지 않고 규칙으로 만듦 (로컬에서 Gemini 키가 없을 때, `LLM_MOCK=true`일 때) |
| 시연 데이터 | 합성 자료이며 LLM을 실행해 만든 것이 아님. 그런데 문서 메모는 "{모델명} 초안"으로 표시됨 (커밋 e773ae8 기준. 시연 데이터 코드는 현재 다른 작업에서 수정 중이라 달라질 수 있음) |

프롬프트만으로는 "어떻게 만드는지"가 다 설명되지 않습니다. 결과물의 일부는 LLM이 아니라 코드가 만듭니다.

| 단계 | LLM이 하는 일 | 코드가 하는 일 |
|---|---|---|
| 3. PRD | 1~12장 본문 작성 (temperature 0.3) | 머리글(제목·버전·작성일·근거)과 변경 이력 작성, 12개 장이 모두 있는지 검사, 빠지면 1회 재시도, 코드 블록 감싸기 제거 |
| 4·5. 검토 | 요구사항별 판정 JSON만 작성 (temperature 0.2) | PRD 표에서 FR·NFR 목록 추출, 응답 형식 제한(요구사항 ID·행 수 고정), 빠진 요구사항은 "확인 불가"로 채움, 요약 건수 계산, 리포트 md 작성, 문서는 앞 6만 자만 전송, QA 검토에는 Architecture를 넣지 않음 |

## 3. 공개 원칙

1. **원문 그대로:** 프롬프트를 요약하거나 다듬지 않습니다. 시스템 지시문, 작업 지시문, 응답 형식(JSON 스키마), 모델, temperature를 모두 보여 줍니다.
2. **한 곳에서 가져오기:** 화면용 문구를 따로 쓰지 않습니다. 실제 호출에 쓰는 코드의 상수와 조립 함수에서 화면 내용을 만듭니다. 그래야 프롬프트를 고쳤을 때 화면이 자동으로 따라옵니다.
3. **프롬프트 밖의 처리도 함께:** 2장의 "코드가 하는 일"을 프롬프트와 같은 자리에 표시합니다.
4. **실제와 다른 경우를 숨기지 않기:** 모의 LLM으로 만든 문서, 시연용 합성 문서, 사용자가 편집한 버전은 "이 프롬프트로 만든 결과"라고 표시하지 않습니다.
5. **비밀값 제외:** 프롬프트에는 API 키나 계정 정보가 없습니다(확인함). 실제 전송본에는 메일·문서 내용이 들어가므로 열람 범위는 기존 업무 데이터와 같게 둡니다.

## 4. 어디에 어떻게 보여 줄지

세 곳에 보여 주는 것을 제안합니다. 역할이 서로 다릅니다.

| # | 위치 | 답하는 질문 | DB 변경 |
|---|---|---|---|
| A | 개발사항 상세의 **단계 설명 카드** (3·4·5단계) | 이 단계는 어떻게 작성·검토하나 | 없음 |
| B | **문서 카드**의 버전별 출처 줄 (PRD, 검토 리포트) | 지금 보고 있는 이 버전은 무엇으로 만들어졌나 | 있음 |
| C | 머리글의 **"프롬프트 공개" 페이지** | 이 시스템이 쓰는 프롬프트 전체는 무엇인가 | 없음 |

### A. 단계 설명 카드: "작성 방식" 영역 (핵심)

3·4·5단계를 선택하면 지금의 "사용자가 할 일 / 시스템이 하는 일 / 완료 조건" 아래에 "작성 방식" 영역을 추가합니다. 흐름 요약은 **항상 보이고**, 원문은 펼쳐서 봅니다.

```
┌ 3단계 PRD 작성·공유 ─────────────────────────────────────────┐
│ [사용자가 할 일]   [시스템이 하는 일]   [완료 조건]            │
│                                                              │
│ 작성 방식                                    Gemini · {모델명} │
│ ① 입력 자료        ② LLM 지시(프롬프트)     ③ 코드가 하는 처리 │
│  · 수집 회신 본문    · 시스템 지시문 7줄       · 머리글·변경 이력 │
│  · 2단계 점검 결과   · 작업 지시문            · 12개 장 검사     │
│  · 질문별 담당자 답  · 12개 장 양식           · 실패 시 1회 재시도│
│  · 담당자 보완 메모                                             │
│                                                              │
│ ▸ 시스템 지시문 원문        [복사]                             │
│ ▸ 작업 지시문 원문          [복사]                             │
│ ▸ 응답 형식 (4·5단계: JSON 스키마)                             │
│ 프롬프트 식별값 a1b2c3d4 · 전체 보기(프롬프트 공개 페이지)      │
└──────────────────────────────────────────────────────────────┘
```

- **원문 표시 방법:** 고정폭 글꼴, 줄바꿈 유지, 복사 버튼. 자료가 들어가는 자리는 `{수집 회신 본문}`처럼 자리 표시로 보여 주고, 지시문은 한 글자도 바꾸지 않습니다.
- **4·5단계:** 같은 프롬프트를 쓰므로 해당 단계의 문장으로 조립한 결과를 보여 줍니다. 두 단계에서 다른 부분(판정 초점, 시험 누락 점검)은 표시해 둡니다.
- **프롬프트 식별값:** 지시문 원문의 해시 앞 8자리입니다. 프롬프트가 바뀌면 값이 바뀌므로, B에서 "이 버전은 지금과 다른 프롬프트로 만들어졌다"를 알릴 수 있습니다.
- **현재 실행 방식 표시:** Gemini면 모델명, 모의 LLM이면 "모의 LLM(규칙 기반) — 지금은 이 프롬프트를 쓰지 않습니다"라고 표시합니다.

### B. 문서 카드: 버전별 출처 줄

PRD와 검토 리포트 카드의 파일명 아래에, 선택한 버전의 출처를 한 줄로 보여 줍니다.

| 버전 종류 | 표시 |
|---|---|
| LLM 생성 | `v3 · Gemini {모델명} 생성 · 프롬프트 a1b2c3d4 · [보낸 프롬프트 보기]` |
| 프롬프트가 그 뒤 바뀐 경우 | 위 표시 + "현재 프롬프트와 다름" |
| 사용자 편집 | `v4 · 사용자 편집 (v3 기준)` |
| 모의 LLM | `v1 · 모의 LLM(규칙 기반) · 프롬프트 미사용` |
| 시연용 합성 | `v1 · 시연용 합성 자료 · LLM 실행 기록 없음` |
| 기록 이전에 만든 문서 | `v2 · 생성 기록 없음 (기록 기능 추가 전)` |

"보낸 프롬프트 보기"를 누르면 그 버전을 만들 때 **실제로 보낸 전문**(자료가 채워진 상태)과 모델, temperature, 시도 횟수, 일시를 창으로 보여 줍니다. 복사와 내려받기를 제공합니다.

이를 위해 실행 기록 테이블을 추가합니다(마이그레이션 `0008`). 저장 방식은 6장 확인 3에서 정합니다.

### C. "프롬프트 공개" 페이지

머리글의 "미분류함", "설정" 옆에 "프롬프트 공개"를 둡니다. 개발사항을 열지 않아도 전체를 볼 수 있어 설명·시연에 씁니다.

- 작업별 카드: PRD 작성(L2), Architecture 검토(L4), QA 검토(L5). 내용은 A와 같은 원문입니다.
- 공통 원칙: 자료 속 지시문 무시(G-04), 자료에 없는 내용은 "확인 필요"(G-02), 형식 오류 시 1회 재시도 후 보류(G-05), 판단은 사람이 함.
- 현재 실행 방식(Gemini 모델 또는 모의)과 작업별 모델 설정.

## 5. 구현 순서

| 순서 | 내용 | 규모 |
|---|---|---|
| 1 | 프롬프트 조립 함수를 "지시문"과 "자료" 부분으로 나누고, 공개용 정보(지시문 원문, 스키마, 설정, 입력 목록, 코드 처리 목록, 식별값)를 한 모듈에서 내보냄. 조립 결과가 지금과 글자 단위로 같은지 테스트로 확인 | 작음 |
| 2 | A(단계 설명 카드)와 C(공개 페이지), 조회 API `GET /api/prompts` | 작음 |
| 3 | 실행 기록 저장(마이그레이션 `0008`), B(버전별 출처 줄, 보낸 프롬프트 보기) | 중간 |
| 4 | (선택) 6장 확인 2·5의 결정에 따라 2단계 점검 프롬프트, 공유 메일 표기 추가 | 작음 |

- 1·2번만으로 "프롬프트 원문 공개"는 충족됩니다. DB를 바꾸지 않습니다.
- 3번은 "이 문서가 그 프롬프트로 만들어졌다"를 증명하는 단계입니다.
- 설계·시험 문서는 6장 확인 6의 결정에 따라 작성하고, 자동 시험에 TC ID를 붙입니다.

## 6. 확인이 필요한 사항

| # | 질문 | 제안 |
|---|---|---|
| 1 | 공개 대상: 로그인한 사용자에게만 보여 줄지, 로그인 없이 볼 수 있는 페이지도 둘지 | 로그인한 사용자에게만. 지금은 모든 화면이 로그인 뒤에 있음 |
| 2 | 범위: 3·4·5단계만 할지, 2단계(수집 내용 검토) 프롬프트도 포함할지. PRD 프롬프트에는 2단계 점검 결과가 입력으로 들어감 | 3·4·5단계를 먼저 하고, 3단계 화면에 "입력인 점검 결과는 2단계에서 만든다"고 표시. 2단계는 같은 구조로 뒤에 추가 |
| 3 | 실제 전송본 저장 방식: (가) 보낸 전문을 그대로 저장, (나) 지시문만 저장하고 자료는 원본 문서를 연결 | (가). 글자 그대로 남는 가장 확실한 방법. 검토 한 번에 최대 약 12만 자(PRD 6만 + 대상 문서 6만)가 저장되어 DB 사용량이 늘어남 |
| 4 | 시연 데이터 표기: 시연 문서를 "시연용 합성 자료 · LLM 실행 기록 없음"으로 표시할지. 현재 메모는 "{모델명} 초안" | 표시함. 투명 공개가 목적이면 합성 자료를 LLM 결과처럼 보이게 두면 안 됨. 시연 때는 "실제 생성 시에는 이 프롬프트를 씁니다"로 안내 |
| 5 | 공유 메일로 나가는 PRD·리포트에 작성 방식을 넣을지 (받는 사람은 사이트에 접속하지 못함) | 이번 범위에서 제외. 필요하면 문서 끝에 프롬프트 식별값 한 줄만 추가 |
| 6 | 문서 단계: 새 단계 P6으로 설계·시험 문서를 만들지, P3·P4 문서에 추가할지 | P6 "프롬프트 공개"로 분리 (`docs/dev/P6_프롬프트-공개.md`, `docs/test/P6_시험.md`) |

## 7. 범위 밖

- 프롬프트 내용 자체의 수정·개선
- 화면에서 프롬프트를 편집하는 기능
- L3(메일 분류), L6(진행상황 해석) 프롬프트 공개 (같은 구조로 나중에 추가 가능)
