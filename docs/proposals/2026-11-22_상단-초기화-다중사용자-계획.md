# 상단 초기화·다중 사용자 계획안

## 1. 요청과 현재 상태

- 상단에 데이터를 초기화하고 시연 데이터를 다시 넣는 버튼을 둔다.
- 약 5명이 각자의 ID·비밀번호로 로그인하며, 각 로그인에 연결된 Gmail 주소·앱 비밀번호·수집 요청 수신 주소를 사용한다.
- 현재 로그인과 메일 설정은 각각 환경 변수 하나의 계정에만 대응한다. 메일 수신 위치, 수신 중복 관리와 발송 한도도 사용자별로 분리되어 있지 않다.
- 현재 시연 초기화는 시연 자료를 구별하지 않고 업무 테이블 전체를 삭제한다. 수신 위치는 그대로 남는다. 삭제 후 생성 중 실패하면 빈 상태 또는 일부만 생성된 상태가 될 수 있다.

## 2. 결정된 운영 방식과 설계 방향

### 시연 데이터와 상단 버튼

1. **결정:** 같은 사이트에서 로그인한 모든 사용자가 상단 버튼으로 공유 시연 데이터만 초기화·재생성한다. 실제 업무 데이터는 삭제하지 않는다.
2. 버튼은 다른 사용자와 공유하는 시연 자료가 삭제됨과 되돌릴 수 없음을 확인한 뒤 `초기화 후 시연 데이터 생성`을 실행한다. 처리 중 중복 실행을 막고 성공·실패와 결과를 명확히 표시하며 완료 후 화면을 갱신한다. 서버에서도 로그인과 대상 범위를 검증한다.
3. 시연 자료에 명시적인 범위 식별자를 두고 관련 레코드의 생성·수정·삭제와 참조 관계를 일관되게 관리한다. 시연 자료와 실제 자료가 연결되어 실제 자료 삭제나 훼손이 발생하지 않도록 서버·DB에서 보호한다. 사용자는 현재 사이트의 자료가 모두 시연 자료이며 초기화 대상에 포함해도 된다고 확인했다. 단, 적용 시점에 추가된 실제 자료가 없음을 재확인하고 백업·복구를 검증한 후 일회성 이전한다.
4. 삭제·재생성 실패 및 동시 실행에 대비해 잠금과 원자적 전환 또는 복구 가능한 방식의 적용 가능성을 DB 연결 방식별로 검증한다. 기존 전역 초기화 API와 CLI도 동일한 보호 범위로 제한한다.
5. 시연 자료는 자연스러운 업무 내용으로 표시하되 내부적으로 합성 출처를 구분하고, 실제 메일 발송·수신 또는 Gemini 실행 기록으로 취급하지 않는다. 시연 데이터가 실제 수신자에게 발송되지 않도록 서버에서 막는 방안을 상세 설계한다.

### 로그인과 메일 설정

1. 사용자별 고유 ID를 세션에 연결하고 서버에서 사용자 활성 상태·권한을 확인한다. 비밀번호는 복구 불가능한 안전한 해시로 검증하고 로그인 시도 제한, 계정 비활성화, 비밀번호 변경·초기화 시 세션 무효화를 제공한다. `AUTH_SECRET`은 계속 서버에서 세션 보호에만 사용한다.
2. **결정:** 관리자가 계정을 추가하고 비밀번호를 초기화한다. 계정별 Gmail 주소·앱 비밀번호·수집 수신 주소는 관리자가 Vercel 환경 변수로 관리한다. 로그인 사용자의 고유 식별자와 설정을 서버에서 연결하고, 사용자에게 비밀번호 원문이나 비밀 환경 변수 값을 반환하지 않는다. 변경 시 배포 환경 반영·재배포 절차를 안내한다.
3. **결정(2026-11-22 추가):** 로그인한 사용자가 설정 화면 ‘내 메일 설정’에서 본인의 Gmail 주소·앱 비밀번호·수집 요청 주소를 직접 수정한다. 값은 DB `user_settings`(마이그레이션 0007)에 저장하고, 앱 비밀번호는 AES-256-GCM으로 암호화한다(키: `SETTINGS_ENCRYPTION_KEY`, 없으면 `AUTH_SECRET`에서 파생). 입력값이 비어 있으면 관리자 환경 변수(`USER_<ID>_*` 또는 전역 `GMAIL_*`)를 쓴다. 앱 비밀번호는 화면·응답에 다시 내보내지 않는다(설정 여부만). AGENTS.md 5-3에 예외로 기록했다.
4. 수집 요청·진행 요청·공유·연결 테스트·메일 확인 전부 로그인 사용자에게 연결된 계정을 사용한다. 자동 발송은 해당 계정의 설정된 수집 수신 주소로만 하고, 공유는 사용자가 수신자를 확인하고 버튼을 눌렀을 때만 발송한다.
5. IMAP 수신 위치·수신 중복·폴링 잠금·발송 한도는 사용자와 실제 메일함을 고려해 분리한다. **결정:** 사이트를 열어 둔 사용자의 메일함만 자동 확인하며 외부 크론은 사용하지 않는다. 한 메일함을 여러 사용자가 공유하는 경우의 중복 및 접근 정책은 별도로 확정한다.
6. **결정:** 업무 데이터는 공유하고 메일 계정만 사용자별로 분리한다. 공유 업무 데이터에 포함된 메일·문서와 미분류 자료는 다른 로그인 사용자에게도 보일 수 있다. 사용자별 자격 증명과 메일함의 수신 위치는 공유하지 않는다.

## 3. 진행 순서

1. 결정 사항과 남은 미결 사항을 서비스 정의와 개발·시험 문서에 반영한다.
2. 시연/업무 데이터의 현황을 확인하고 백업·복구를 검증한다. 시연 범위 식별 및 기존 초기화 경로 보호를 구현한 후 상단 버튼을 추가한다.
3. 사용자·세션·권한을 추가한다. 스키마 변경이 필요하면 새 마이그레이션을 추가하며 기존 단일 계정과 자료의 이전 및 롤백을 준비한다.
4. 사용자별 메일 설정과 송수신·폴링·크론을 연결한다. 실제 메일 주소·앱 비밀번호는 저장소나 테스트 자료에 넣지 않는다.
5. 합성 자료로 계정 간 접근, 권한 우회, 잘못된 설정, 초기화 중 실패·동시 실행, 기존 데이터 보존, 수신 중복, 발송 대상 제한을 시험한다. 자동 테스트·타입 검사·린트와 배포 전 브라우저 검증을 수행한다.
6. 사용자 승인 후 GitHub·Vercel에 반영하고 같은 사이트에서 실제 업무 데이터 보존과 시연 초기화를 확인한다. 실제 Gmail 송수신은 대상자 동의 후 확인하며 미확인 항목은 통과로 기록하지 않는다. 업무 사용 시 Vercel 요금제와 보안·운영 적합성도 확인한다.

## 4. 남은 확인 사항

- 배포 전 Neon 백업(브랜치)과, 배포 시점까지 실제 업무 자료를 넣지 않았는지 확인 (마이그레이션 0006이 기존 자료를 모두 시연으로 표시).
- 같은 메일함을 여러 사용자가 공유할 때: 같은 Message-ID는 한 번만 기록되므로 중복은 생기지 않지만, 수신 위치는 Gmail 주소별로 하나다.
- 시연 생성 중 실패 시에는 시연 데이터를 비우고 오류를 알린다(다시 누르면 복구). Neon HTTP 연결은 여러 문장을 묶는 트랜잭션을 지원하지 않아 원자적 교체 대신 이 방식을 택했다.
