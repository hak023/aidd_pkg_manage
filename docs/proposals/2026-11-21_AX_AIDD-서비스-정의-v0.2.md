### 1.2 서비스 한 줄 정의

> 개발사항마다 **메일로 사내 논의 내용을 수집**하고, **LLM으로 점검**해 PRD를 만들고, 개발사가 보낸 **Architecture·QA 문서를 PRD와 대조**하며, **진행상황을 추적·공유**하는 개발 BA용 웹 서비스.

### 1.3 범위

| 포함 | 제외 |
|---|---|
| 단위서비스 > 라벨링 > 개발사항 트리 관리 (생성·이름 변경·드래그 이동) | 다중 사용자, 실제 인증·권한, 세션 관리 |
| 개발사항별 진행 단계(progress) 관리 | 회사 PC 쪽 자동화 (Copilot 회신은 사용자가 직접 요청·발송) |
| Gmail 발송·수신 (수집 요청, 진행상황 요청, 공유, 개발사 문서 수신) | Outlook·Teams·Confluence 직접 연동 (회사 PC의 Copilot이 대신함) |
| Gemini로 수집 내용 점검, PRD 생성, Architecture·QA 점검, 메일 분류 | 개발 타당성·설계·FP·시험 합격의 자동 판단 |
| md 파일 생성·편집·버전 관리·첨부 공유 | ERP 등 업무 시스템 입력 |
| 시뮬레이터 모드 (가상 메일함 + 샘플 메일) | |

## 2. 데이터 구조: 트리

```
단위서비스 (예: 통화매니저)                 ← 최상위, N개
 └ 라벨링 (예: R181PKG_26.12)               ← N개
    └ 개발사항 (예: 통화매니저 SSO 로그인 기능 개발)   ← N개, 진행 단계를 가짐
```

**UI 제안**
- **화면 구성:** 왼쪽은 트리 패널, 오른쪽은 선택한 항목의 상세 화면입니다.
- **생성:** 상단 `+ 새로 만들기` 버튼에서 유형(단위서비스 / 라벨링 / 개발사항)과 상위 항목을 선택합니다. 각 노드에 마우스를 올리면 `+`(하위 항목 추가), 이름 변경, 삭제 메뉴가 나옵니다.
- **드래그로 이동:**
  - 개발사항은 다른 라벨링 아래로 옮길 수 있습니다.
  - 라벨링은 다른 단위서비스 아래로 옮길 수 있고, 하위 개발사항도 함께 이동합니다.
  - 허용되지 않는 위치에 놓으면 이동을 막고 이유를 표시합니다.
- **삭제:** 하위 항목이 있으면 경고하고, 확인을 받은 뒤 처리합니다.
- **첫 화면(대시보드):** 전체 개발사항을 표로 보여 줍니다(현재 단계, 마지막 메일 수신일, 다음 할 일).
- **개발사항 추가 입력 (모두 선택 사항):** 검색 키워드, 검색 기간, 메모. Copilot이 관련 자료를 더 정확히 찾게 하는 데 씁니다.

## 3. 진행 단계 (Progress)

개발사항 상세 화면 위쪽에 **가로 단계 그래프**를 두고, 단계마다 "지금 무엇을 하면 되는지" 설명을 표시합니다.

| # | 단계 | 시작 조건 | 사용자 행동 | 시스템 동작 | 완료 조건 |
|---|---|---|---|---|---|
| 1 | **개발 내용 수집** | 개발사항 생성 | `수집 요청 메일 보내기` | 수집 요청 메일을 config에 지정된 회사 주소로 발송 → 회신 대기 | 태그가 맞는 회신 메일 수신 |
| 2 | **수집 내용 검토** | 1 완료 | LLM 점검 결과를 확인하고 추가 내용을 텍스트로 입력 | 회신을 구조화하고, 부족한 항목·상충 내용·추가 확인 질문을 표시 | `PRD 생성` 실행 |
| 3 | **PRD 작성·공유** | 2 완료 | PRD 확인·편집 → `공유` (수신자 편집 가능) | `{단위서비스}_{라벨링}_{개발사항}_PRD.md` 생성, 버전 기록 | PRD 공유 메일 발송 |
| 4 | **Architecture 검토** | 3 완료 | 검토 리포트 확인·편집 → `공유` | 수신된 md를 분류·매칭해 자동 등록하고, PRD 대비 반영 여부를 점검한 리포트 생성 | Architecture md 등록 (자동으로 진행) |
| 5 | **QA(시험항목서) 검토** | 4 완료 | 4단계와 동일 | 4단계와 동일 (요구사항별 시험 항목 커버리지 점검) | QA md 등록 |
| 6 | **진행상황 체크** | 5 완료 | `진행상황 요청 메일 보내기` → 확인 → `공유` | 회신을 파싱해 마일스톤 표 생성 (값이 없으면 "미정") | 진행상황 회신 수신 |
| 7 | **완료** | 6 이후 | `완료` 버튼 | 상태를 완료로 바꾸고 이력 기록 | — |

**단계 운영 규칙 (확정)**
- **순서 강제 없음:** 단계마다 상태를 따로 가집니다(대기 / 진행중 / 완료). 어느 단계든 언제든 실행할 수 있습니다. 예를 들어 QA가 Architecture보다 먼저 오면 QA 단계가 먼저 완료됩니다. "시작 조건" 열은 권장 순서일 뿐입니다.
- **현재 단계 표시:** 완료되지 않은 단계 중 가장 앞의 단계를 "현재 단계"로 보여 줍니다.
- **재요청:** 수집 요청과 진행상황 요청은 여러 번 보낼 수 있습니다. 회신이 새로 오면 새 버전으로 쌓입니다.
- **개정본:** Architecture나 QA 개정본이 다시 오면 새 버전으로 등록하고, 점검 리포트를 다시 생성합니다.
- **이력:** 단계 변경은 모두 날짜와 함께 이력에 남깁니다.

## 4. 메일 연동 설계 (요청 5번 방안)

### 4.1 전체 구조

```
[웹사이트]                          [Gmail 계정]                [회사 PC: Outlook + Copilot]
 수집 요청 버튼 ── 발송 ──────────▶  보낸편지함  ── 메일 ──────▶  수신 (회사 메일 주소, config)
                                                                   │ 사용자: "메일 내용 회신내용 작성해줘"
                                                                   │ Copilot: Outlook·Teams·Confluence 검색 후 양식대로 작성
 수신 확인(폴링) ◀── 받은편지함 ◀──── 회신 ─────────────────────  사용자 검토 후 회신
   │
   ├ 제목 태그로 개발사항 매칭
   ├ 회신 양식 구간 추출 → Gemini로 구조화·점검
   └ 진행 단계 이동
```

### 4.2 메일 매칭 방법: 제목 태그

모든 발송 메일 제목에 **추적 태그**를 넣습니다. 회신하면 `RE:`가 붙어도 태그가 유지되므로 개발사항을 확실히 찾을 수 있습니다.

```
[AX_AIDD][DEV-0001][수집요청] 통화매니저 / R181PKG_26.12 / 통화매니저 SSO 로그인 기능 개발
[AX_AIDD][DEV-0001][진행상황요청] 통화매니저 SSO 로그인 기능 개발
```

- **보조 수단:** 메일 헤더(`In-Reply-To`)와 본문의 시작·끝 표식(`<<<AX_AIDD_REPLY_START DEV-0001>>>`)도 함께 확인합니다.
- **개발사 문서 전달 (Q-03 확정):** 사용자가 회사 메일에서 Gmail로 전달합니다. 전달할 때 제목에 태그를 붙이면 확실하게 매칭됩니다. 예: `[AX_AIDD][DEV-0001] FW: 아키텍처 설계서`. 개발사항 상세 화면에 "전달용 제목 복사" 버튼을 둡니다.
- **태그가 없는 전달 메일:** Gemini가 첨부 md의 내용으로 문서 유형과 해당 개발사항을 추정합니다.
  - 확신도가 높으면 자동 등록합니다.
  - 확신도가 낮으면 **미분류함**에 넣고 사용자가 지정합니다.

### 4.3 수집 요청 메일 작성 방안

핵심은 Copilot이 메일을 읽고 **그대로 따라 할 수 있는 지침**과 **정해진 회신 양식**을 메일 본문에 넣는 것입니다. 회신이 양식을 따르면 웹사이트가 안정적으로 해석할 수 있습니다.

메일 본문은 세 부분으로 구성합니다.

1. **사람용 안내 (2~3줄):** "이 메일을 연 상태에서 Copilot에게 '메일 내용 회신내용 작성해줘'라고 요청하고, 결과를 검토한 뒤 회신하세요. 제목의 태그는 지우지 마세요."
2. **Copilot 작성 지침**
   - 대상 개발사항: 단위서비스, 라벨링, 개발사항명
   - 검색 범위: 내 Outlook 메일, Teams 채팅·채널·회의록, Confluence(접근 가능한 경우)
   - 검색 키워드와 기간: 개발사항에서 입력한 값을 사용하고, 없으면 개발사항명과 최근 6개월로 둡니다.
   - 작성 규칙:
     - 섹션 제목과 순서를 바꾸지 않습니다.
     - 모든 내용에 출처를 답니다: `[Teams 2026-10-02 홍길동 "채널명"]` 형식
     - 찾지 못한 항목은 **"확인 안 됨"**으로 씁니다. 추측하지 않습니다.
     - 의견이 서로 다르면 모두 적고 `[상충]`으로 표시합니다.
     - 비밀번호, 개인 휴대폰 번호, 고객 개인정보는 넣지 않습니다.
3. **회신 양식:** 4.4의 항목을 시작·끝 표식 사이에 둡니다.

**Copilot 요청 경로**

| 경로 | 방법 | 비고 |
|---|---|---|
| **기본 경로 (사용자 안)** | Outlook에서 메일을 열고 Copilot에게 "메일 내용 회신내용 작성해줘" 요청 | 가장 간단함. 다만 Outlook 회신 초안 기능이 Teams·Confluence까지 검색하는지는 **사전 테스트가 필요**합니다 |
| **보조 경로** | 메일의 지침 블록을 복사해 Microsoft 365 Copilot Chat(업무 모드)에 붙여 넣고, 결과를 회신 본문에 붙여 넣음 | 기본 경로의 검색 범위가 부족할 때 사용 |

Confluence는 조직에서 Copilot 커넥터를 설정해 둔 경우에만 검색됩니다. 검색되지 않으면 회신의 출처 목록에 "Confluence 검색 불가"라고 적도록 지침에 넣습니다.

**바로 해 볼 수 있는 일:** 부록 A의 메일 예시를 회사 메일로 직접 보내 보고, Copilot 회신 품질과 검색 범위를 먼저 확인해 보시길 권합니다. 구현 전에 이 방식이 실제로 통하는지 검증하는 가장 빠른 방법입니다.

### 4.4 수집할 정보 (요청 6번 제안)

PRD 양식(5.3)과 공유 수신자(3단계)에 필요한 정보를 기준으로 정했습니다.

| # | 섹션 | 수집 내용 | 쓰이는 곳 |
|---|---|---|---|
| 01 | **관련자** | 이름, 부서, 역할(요청·결정·개발·운영·검증), 이메일 | **공유 수신자 기본값**, PRD 이해관계자 |
| 02 | **요청 배경** | 누가, 언제, 왜 요청했는지. 고객·VoC·정책 등 계기 | PRD 배경 |
| 03 | **히스토리 (의사결정 과정)** | 날짜순: 일자, 채널(메일·Teams·Confluence·회의), 참여자, 논의 내용, 결정 사항 | PRD 히스토리 |
| 04 | **기존 문제점·현행 방식** | 지금 어떻게 동작하고 무엇이 불편한지 | PRD 기존 문제점 |
| 05 | **목표·기대효과** | 달성하려는 상태, 언급된 지표 | PRD 목표 |
| 06 | **요구사항** | 기능 요구사항(예: SSO 방식, 대상 사용자, 로그인·로그아웃·세션 만료 처리, 실패 처리) / 비기능 요구사항(성능·보안·가용성) | PRD 요구사항, Architecture·QA 점검 기준 |
| 07 | **범위·비범위** | 이번에 할 것과 하지 않을 것 | PRD 범위 |
| 08 | **연동 시스템·부서** | 연동 대상(예: IdP, 인증 서버), 인터페이스, 담당 부서, 협의 상태 | PRD 연동, Architecture 점검 |
| 09 | **제약·보안·운영 고려** | 보안 심의, 운영 절차, 장애 대응, 호환성 | PRD 제약 |
| 10 | **일정** | 언급된 마일스톤, 목표 PKG(라벨링)와의 관계 | PRD 일정, 진행상황 |
| 11 | **미결·쟁점** | 결정되지 않은 사항, `[상충]` 항목 | LLM 점검, 추가 질문 |
| 12 | **참고 자료·출처** | 문서명, 링크, 일자, 검색하지 못한 범위 | PRD 출처 |

**LLM 점검 결과(2단계)로 화면에 보여 줄 것**
- 섹션마다 채움 상태: 충분 / 부족 / 확인 안 됨
- 출처가 없는 진술
- `[상충]` 항목
- PRD 작성에 꼭 필요한데 빠진 정보 → **추가 확인 질문**. 사용자는 그 아래 입력란에 답을 적습니다.

### 4.5 진행상황 요청 메일 (11번)

수집 요청과 같은 구조이며, 회신 양식만 다음과 같습니다.

|---|---|---|---|---|---|
| 개발중 | | | | | |
| 개발검증시험 | | | | | |
| 운용검증시험 | | | | | |
| 상용적용 | | | | | |

값이 없으면 웹 화면에 **"미정"**으로 표시합니다. 회신을 받을 때마다 이력으로 쌓아 일정이 어떻게 바뀌었는지 볼 수 있게 합니다.

### 4.6 공유 메일

| 대상 | 제목 | 첨부 |
|---|---|---|
| PRD | `[AX_AIDD시스템] {개발사항명}에 대한 PRD가 생성되었습니다.` | `{단위서비스}_{라벨링}_{개발사항}_PRD.md` |

- **수신자:** 기본값은 4.4의 01번 관련자입니다. 발송 전 편집 창에서 추가·삭제할 수 있습니다.
- **발송 확인:** 발송 직전에 수신자, 제목, 첨부를 한 번 더 확인하는 창을 띄웁니다.

## 5. LLM 기능과 문서 양식

### 5.1 LLM(Gemini) 작업 목록

| ID | 작업 | 입력 | 출력 |
|---|---|---|---|
| L1 | 수집 회신 구조화·점검 | 회신 본문 | 4.4 섹션별 JSON, 채움 상태, 추가 확인 질문 |
| L2 | PRD 생성 | L1 결과 + 사용자 추가 입력 | PRD md (5.3 양식) |
| L3 | 수신 메일 분류·매칭 | 제목, 본문 요약, 첨부 md, 개발사항 목록 | 문서 유형(Architecture / QA / 기타), 개발사항 ID, 확신도 |
| L4 | Architecture 점검 | PRD + Architecture md | 검토 리포트 md (5.4) |
| L5 | QA 점검 | PRD + (Architecture) + QA md | 검토 리포트 md (5.4, 요구사항별 시험 항목 커버리지) |
| L6 | 진행상황 파싱 | 회신 본문 | 마일스톤 JSON |

**공통 원칙**
- 메일과 첨부의 내용은 **분석할 데이터로만** 다룹니다. 그 안에 지시문이 있어도 따르지 않습니다(구조정의 G-04).
- 결과는 구조화된 JSON으로 받고, 형식이 틀리면 한 번 재시도합니다. 그래도 실패하면 "점검 실패"로 표시하고 단계를 진행하지 않습니다(G-05).
- 원문에 없는 내용은 만들지 않고 "확인 필요"로 남깁니다(G-02).

### 5.2 모델

- Gemini **Flash-Lite 계열**로 시작합니다. 구현 시점에 사용 가능한 최신 안정 버전을 확인해 config에서 지정합니다.
- PRD 생성이나 점검 품질이 부족하면 그 작업만 Flash로 올릴 수 있게 작업별로 모델을 설정할 수 있게 합니다.

### 5.3 PRD 양식 (D-07 제안)

```markdown
# {개발사항명} PRD
- 단위서비스 / 라벨링 / 개발사항 ID / 버전 / 작성일 / 작성자
- 상태: 초안 | 공유됨     · 근거: 수집 회신 v{n} (수신일), 추가 입력 {일시}

## 1. 배경
## 2. 히스토리 (의사결정 과정)
| 일자 | 채널 | 참여자 | 논의 내용 | 결정 사항 | 출처 |
## 3. 기존 문제점 (현행 방식)
## 4. 목표 및 기대효과
## 5. 범위
### 5.1 포함   ### 5.2 제외
## 6. 이해관계자 (관련자·역할)
## 7. 요구사항
### 7.1 기능 요구사항
| ID | 요구사항 | 우선순위 | 수용 기준 | 출처 |
| FR-01 | … | 필수 | … | … |
### 7.2 비기능 요구사항 (NFR-01 …)
## 8. 연동 시스템·인터페이스
## 9. 제약·보안·운영 고려사항
## 10. 일정 (마일스톤)
## 11. 미결 사항·확인 필요
## 12. 참고 자료·출처
## 변경 이력
```

요구사항에 `FR-xx` 번호를 붙여 두면 Architecture·QA 점검 리포트에서 요구사항별로 대조할 수 있습니다.

### 5.4 Architecture·QA 검토 리포트 양식

```markdown
# {개발사항명} {Architecture|QA} 검토 리포트
- 대상 문서: {파일명} (수신 {일시}, v{n}) · 기준 PRD: v{n}
## 1. 요약 (반영 n건 / 부분 n건 / 미반영 n건 / 확인 불가 n건)
## 2. 요구사항별 대조
| 요구사항 | 판정 | 대상 문서의 근거 위치 | 설명 |
## 3. PRD에 없는 추가 내용 (범위 확인 필요)
## 4. 추가 확인 필요 사항 (개발사에 보낼 질문)
## 5. 검토자 메모 (사용자 편집)
```

- **QA 리포트에 추가로 넣을 점검:** 예외·실패 케이스, 비기능 시험, 회귀 시험의 누락
- **판정의 의미:** 리포트는 **문서상 대조 결과**일 뿐이며 실제 시험 합격을 뜻하지 않는다는 문구를 넣습니다.
- **편집:** 웹 편집기에서 수정하면 새 버전으로 다시 등록됩니다.

## 7. 기술 구성과 무료 배포 (D-05)

### 7.1 추천 구성

| 영역 | 선택 | 무료 조건과 주의점 |
|---|---|---|
| 웹 앱 | **Next.js (TypeScript)** | |
| 호스팅 | **Vercel Hobby** → `프로젝트명.vercel.app` 공인 주소 | **Hobby 요금제는 개인·비상업 용도 조건**이므로 회사 업무 용도로 써도 되는지 확인이 필요합니다. 함수 실행 시간에 제한이 있어 긴 LLM 작업은 나눠서 처리합니다 |
| DB | **Neon Postgres (무료)** | 사용하지 않으면 자동으로 멈췄다가 접속하면 다시 켜짐 (첫 요청이 조금 느림). md 파일 내용도 DB에 저장 |
| 메일 | **Gmail 앱 비밀번호 + SMTP(발송)/IMAP(수신)** | Google 계정에 **2단계 인증**이 켜져 있어야 앱 비밀번호를 만들 수 있습니다. OAuth 방식보다 설정이 단순하고, 토큰 만료 관리가 필요 없습니다 |
| 수신 확인 | ① `메일 확인` 버튼 ② 사이트를 열어 둔 동안 1~2분마다 자동 확인 ③ 무료 외부 크론(cron-job.org 등)이 5~10분마다 확인 주소를 호출 | Vercel Hobby의 자체 크론은 하루 1회 수준으로 제한되어 외부 크론을 씁니다 |
| LLM | Gemini API | 아래 7.3 참고 |
| 코드 저장소 | GitHub (비공개 저장소) | Vercel이 저장소에 push될 때마다 자동 배포 |

**대안:** Render 무료 웹서비스를 쓸 수도 있습니다. 15분 동안 사용하지 않으면 잠들고 다시 깨어나는 데 수십 초가 걸리지만, 상업 용도 제한이 없습니다.

### 7.2 config (환경 변수, 저장소에 넣지 않음)

| 키 | 용도 |
|---|---|
| `LOGIN_ID`, `LOGIN_PASSWORD` | 더미 로그인 계정 |
| `GMAIL_ADDRESS`, `GMAIL_APP_PASSWORD` | 시스템용 Gmail 계정 |
| `COLLECT_TO_ADDRESS` | 수집·진행상황 요청 메일을 받을 회사 주소 |
| `GEMINI_API_KEY`, `GEMINI_MODEL_*` | Gemini 키와 작업별 모델 |
| `DATABASE_URL` | Neon 연결 문자열 |
| `POLL_SECRET` | 외부 크론이 메일 확인 주소를 호출할 때 쓰는 비밀값 |
| `SIMULATOR_MODE` | true면 실제 메일 대신 가상 메일함 사용 |
| `AUTH_SECRET` | 로그인 쿠키 서명용 비밀값 |

로그인 상태 유지에는 **서명된 쿠키 하나만** 씁니다. 별도의 세션 저장소나 인증 체계는 만들지 않습니다.

### 7.3 시뮬레이터 (D-02 자체 검증)

- **`SIMULATOR_MODE=true`일 때:** 실제 메일을 보내지 않고 **가상 메일함**에 기록합니다. 관리 화면에서 샘플 수신 메일을 주입할 수 있습니다.
- **샘플 메일:** "통화매니저 SSO 로그인 기능 개발" 기준의 합성 데이터로 4종을 준비합니다.
  1. Copilot 수집 회신
  2. 개발사 Architecture md
  3. 개발사 QA md
  4. 진행상황 회신
- **자동 시나리오 테스트:** 생성부터 완료까지 1~7단계를 자동으로 따라가며 각 단계가 넘어가는지 확인합니다. LLM은 모의 응답으로도, 실제 Gemini로도 돌릴 수 있습니다.
